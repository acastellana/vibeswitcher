# VibeSwitcher 2, the Lead Engine (VibeNode) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `vibeswitcher-server`, the session host's server child, runs the node's lead engine, rebuilt in `VibeNode`
from the non-UI duties of the Mac app's `LeadController`, `SessionStore` and `HostClient`. `vibeswitcher` (built as
`vibeswitcher-cli`) drives it over a versioned request/reply protocol on the server's Unix socket, and every request
that changes state is taken only from the user's voice. Under a scratch host, a lead started from the command line on
a scratch repository plans, asks a question and is answered from the command line; an audit can't hang on a prompt;
the lead hears every report. The Mac app and its tests are untouched.

**Architecture:** `VibeNode` gets stores keyed by id, each a set of `Codable` values with a small change stream
(sessions, leads and their boards, cards), an engine that runs on one serial queue and does its blocking reads on a
second, and `HostLink`, the engine's one view of the host. The server reaches the host only through the connector it
inherits (the security document's S2): it registers that connector for its host's socket path, so every `VibeCore`
call that reaches the host (`HostCall`, `LeadVault.standard`, `SteerSeal.host`) goes through it in that process. The
command line is the server's first client: its requests are JSON lines, each with an id, a kind and the voice it needs,
the seed of stage 3's live protocol. What the app asks in a modal dialog is a flag or a card; what the app reads from
`board.json` and shows as the user's choice is built by the engine from git and the vault; what the user answers is
recorded in the host's vault before it is acted on. What happened to the node (starts, restarts, acknowledgments) is
read by the command line from the journal, never taken from the server.

**Tech Stack:** Swift 6.4.2 (language mode 5), SwiftPM `--build-system native`, `VibeCore`, `VibeHost` (tests only),
`VibePlatform`; Foundation's `JSONEncoder`/`JSONDecoder` for the wire; no new dependency.

**Spec:** `docs/superpowers/specs/2026-11-12-vibeswitcher-2-design.md` (VibeNode: stores, not view models; The node's
processes; The live protocol; Rules from the first line; Stage 3 and 4 before the bootstrap). The security document,
`docs/superpowers/specs/2026-11-13-v2-security-architecture.md`: S2 (the server's half of the connector, the journal
the command line reads), S3 (the server's socket, the user's voice, cards, answers at rest), S6 (the server's first

The outline E1 to E8 in [the bootstrap path](2026-11-13-v2-bootstrap-path.md#the-engine). The stage 2 plan
(`2026-11-13-v2-stage-2-session-host.md`). The ledger, `docs/process/v2-port-map.md`.

## Global Constraints

- Everything in stage 1's and stage 2's Global Constraints holds: all work on `v2`; nothing under
  `Sources/VibeSwitcher`, `Tests/VibeSwitcherTests` or `Web/` is edited; tests only through `scripts/test.sh`; agents
  install nothing; a fix's test is shown failing without the fix; `. ~/.local/share/swiftly/env.sh` first; every job
  green before the next task's first push, under stage 1 R3's time box for Mac-only failures.
- **Rebuilt, not moved.** `VibeNode`, `vibeswitcher-server` and `vibeswitcher-cli` never import the app, AppKit,
  SwiftUI or Combine. A pure helper of the app may be copied (a struct or enum with no view type, no `@Published`, no
  dialog), with a line in the port map's [Copied from the app](../../process/v2-port-map.md#copied-from-the-app). A test
  helper of the app's tests (`FakeClaude`, the non-view parts of `ChatSyncTests`' `Harness`) may be copied the same way.
- **The app's tests are the spec.** Each case this plan ports keeps its assertion; where the engine has no view, the
  case is restated against the engine's store or the command line, and the port map's test table says how.
- **Shared files.** An edit to `Sources/VibeCore`, `Sources/VibeHost` or an executable shared with main is one of
  stage 2's seven kinds, each edit of kinds 4 to 7 listed under [Non-seam edits this plan
  makes](#non-seam-edits-this-plan-makes) and as a planned row in the port map. An executor who needs another stops and
  asks. New `VibeCore` files for version 2 go in `Sources/VibeCore/V2/`, new `VibeHost` ones in `Sources/VibeHost/V2/`,
  which main never has. Every Linux-only switch in a shared file reads `!Platform.CodeIdentity.isAvailable`, its Mac
  form does nothing, and a Mac test says so.
- `PlatformLint` covers `Sources/VibeNode`, `Sources/vibeswitcher-server` and `Sources/vibeswitcher-cli`: no `#if os`,
  no system import. "On Linux" outside `VibePlatform` reads `!Platform.CodeIdentity.isAvailable` (stage 2).
- **The engine's one timer.** The engine refreshes on a 3 s period and the session scan on a 2 s period, on one clock
  (`NodeClock`, the app's `Heartbeat`), with the room watch's 60 s client on the same clock. That is the design's
  recorded exception to "never from a timer"; stage 3's stores remove it. Nothing else in `VibeNode` polls.
- **Tests never reach the user's node**: scratch homes (`VIBESWITCHER_HOME`), scratch hosts on their own lock and
  socket; never the user's `~/.vibeswitcher`, `$XDG_RUNTIME_DIR`, journal or systemd. A command line or server whose
  root comes from `VIBESWITCHER_HOME` (a scratch node) never writes to `/run/systemd/journal/socket` and never runs
  `/usr/bin/journalctl` or `/usr/bin/systemctl`: it uses `<root>/v2/test/journal.sock`, `<root>/v2/test/journalctl`
  and `<root>/v2/test/systemctl` when a test put them there, and otherwise says "scratch node: no journal, no manager".
  Its `claude` is `<root>/v2/test/claude` (EN-D13), never the account's.
  Real agents only in gated tests, on Sonnet, with `VIBESWITCHER_REAL_CLAUDE_CONFIG_DIR` given on the command line of
  the run (the security document's decision 16).
- **One root per test.** No engine, server or `NodeTestHost` in a test process uses that process's `VibePaths.root`:
  each takes its root as a parameter, and each `NodeTestHost` gives its sessions a `HOME` of their own, so the tests
  Swift Testing runs in parallel never share a steer inbox, a state folder or a `server.sock`.
- **Linux-only suites are marked.** A suite that needs a scratch host, the server child or `/proc` carries
  `NodeTraits.linuxOnly` (`.enabled(if: !Platform.CodeIdentity.isAvailable, "…")`, in
  `Tests/VibeNodeTests/NodeTraits.swift`); the Mac's core job runs the rest of `VibeNodeTests`. Each task's Done-when
  says which suites the Mac runs.
- A new suite whose name ends in `LintTests` is named in `docs/guide/development.md`'s lint command.
- Commit messages end with the attribution line the session gives.

## Decisions this plan makes

Each is the author's call (numbered EN-D1 and up) and can be overruled before its task starts. The security
document's decisions that await the user are planned on their recommendations; [If the user answers
otherwise](#if-the-user-answers-otherwise) lists the tasks each would change.

1. **EN-D1: One engine queue.** The app runs `LeadController` on the main thread and its reads on `LeadReads`' queue.
   The engine runs on one serial queue (`LeadEngine.queue`) and its blocking reads (boards, git, transcripts, the
   vault) on a second (`LeadEngine.reads`), in the order asked, exactly as `LeadReads` does. Every app test that says
   "off the main thread" is ported as "off the engine queue".
2. **EN-D2: JSON lines on the server's socket.** One message a line, compact JSON (which never holds a raw newline),
   at most 1 MiB a line; a longer line closes the connection. The same objects become WebSocket text frames in stage
   3. Not `HostFrame`: the host's binary frames carry PTY bytes, which this protocol never does before stage 3.
3. **EN-D3: The server's root and its socket.** The socket is `<root>/v2/server.sock`, 0600, in `<root>/v2/` (0700).
   The user's server (`--node`) takes its root as its host does (`HOME` from `getpwuid`, `VIBESWITCHER_HOME` and
   `CFFIXED_USER_HOME` unset, stage 2 Task 9b). A scratch server takes `--root PATH` from its host (the host's own
   `VibePaths.root`, which stage 2's Task 8a passes to every server child without `--node`) and sets
   `VIBESWITCHER_HOME` to it in its own environment before anything reads `VibePaths`. Every
   server gets `--host-socket PATH` (the host's `config.socketPath`), refuses to start (exit 78, a log line) unless it
   equals `VibePaths.hostSocket.path` under its root, and registers its connector for exactly that path: `VibeCore`'s
   defaults (`HostCall`, `LeadVault.standard`, `SteerSeal.host`) then reach its own host, only through the connector.
4. **EN-D4: Ids carry their node** (rule 1). The node is `local` until nodes have names. A project is
   `local:project:<9 bytes of SHA-256 of "lead|"+standardized root, base64url>` (the phone's `PhoneLeads.id(root:)`
   rule, copied); a hosted session `local:<host uuid, lower case>`; an unhosted one `local:<terminal>` (stage 1's);
   a card `local:card:<uuid>`. A request id is the client's; an action id (a UUID the command line makes once per
   state-changing command and sends again on a retry) survives a server restart (rule 8), so an action is done once.
5. **EN-D5: The typed word is a four-letter code.** Every state-changing request asks, on the command line's
   controlling terminal, for a code printed with what the request will do. No terminal on stdin and no `/dev/tty`:
   refused, saying why. For a request on a card (`answer`, `hold`, `config accept`, `base accept`, `base keep`) the code
   is the card's (derived from its id), sent as the request's `code` and checked by the server, which answers `voice`
   on a mismatch. For a request with no card (`lead`, `stop`) the command line derives the code from the action id and
   checks it alone: a guard rail against a request run without the user's hands, not a check the server makes. So
   `lead`, `stop`, `build.switch` and `hooks` ask it too, and `config held` and `base show`, which change nothing,
   don't; the security document's S3 table now says the same. `status --ack` (a journal entry, EN-D15) asks the
   command line's own code; the reads ask none.
6. **EN-D6: `stop` goes through the server, which ends every session and then asks the host to shut down.** The host
   honours `shutdown` only with no live session (`HostServer.swift:572-577`), and on Linux a lead may spawn
   (`spawnNeedsLead`). So the server stops taking `lead`, ends the leads first, then every other session, and looks
   again until nothing is live (at most 30 s, then it says which sessions remain), then sends `shutdown`. It works the
   same with and without systemd; the bootstrap path's step 8 adds `/usr/bin/systemctl --user stop` (or, without
   systemd, ending the recorded pid) only for a node whose server doesn't answer.
7. **EN-D7: The floor comes from `config accept` on Linux.** The engine never passes `floor:` to
   `LeadVault.startLead` on Linux (the security document's S7: no floor seeded on a fresh vault). `config held` shows
   the floor `workflow.md` proposes beside the held files, and `config accept` records it, in this order: first
   `checkConfig(root:shown:)` with the card's hashes, which seals what was shown and ends that root's first-look hold
   (stage 2's Task 10e), then `setReviewFloor(onlyIfUnset: true)` (app only), which the vault refuses to record while
   the root's first look is still held. The bootstrap clone's floor (decision 13) is in its `workflow.md`, read by the
   user and accepted that way. On the Mac nothing changes (the app keeps seeding it).
8. **EN-D8: The command line checks the server it reached in two forms.** The user's node: the listener is
   non-dumpable, in the node unit's cgroup and a child of the unit's `MainPID` (S3). A scratch node
   (`VIBESWITCHER_HOME` set, and resolving to a folder other than the account's own `~/.vibeswitcher`, the home taken
   from `getpwuid`): non-dumpable and a child of the process holding `<root>/scratch-host.lock`, found by that file's
   inode in `/proc/locks` (`Platform.Processes.lockHolder(path:)`, a new `VibePlatform` call whose Darwin form answers
   nil); every command then prints "scratch node at <root>" on stderr. `VIBESWITCHER_HOME` naming the account's own
   folder gets the user's node's check. No flag or pid is passed (the bootstrap path's step 9 uses this form).
9. **EN-D9: The engine's own state file** `<root>/v2/engine.json` (format 1) keeps what isn't the user's and what a
   restarted server needs to avoid repeating itself: held messages (E5), witness keys already told, auto_advance's
   first sightings, the last host start seen (E8). Nothing in it is taken as the user's: a held `.user` message carries
   the action id of the request that made it, and after a restart it is delivered as the user's only when the vault's
   record of user actions (EN-D11) holds that action with the message's digest; otherwise it goes as
   `.system("vibeswitcher")`, saying it couldn't be vouched for, with a log line.
10. **EN-D10: Questions reach the server from the lead's tool server.** `ask_user`, `revise_question` and
    `withdraw_question` post to the server's socket as well as writing the board (one hook each into
    `Sources/VibeCore/V2/NodeQuestionPost.swift`, which does nothing where `Platform.CodeIdentity.isAvailable`, that
    is on the Mac, or where no server socket exists). A post carries the host's seal of a `.lead` message over the
    post's digest (`LeadVault.seal`, which the host makes only for the lead's own callers); the server takes it only
    when `.verify` says the seal is valid, the poster's `PeerFacts` show no `BranchCode` runner, and the poster's
    session is the one the vault binds to that project's lead role. After a server restart the lead is told which of
    its open questions the user no longer sees, and asks again those it still needs.
11. **EN-D11: User actions and `.user` seals at rest go through one new host request**, made of edits stage 2
    already allows. `HostRequest.vaultV2(LeadVaultV2.Request)`, answered with `HostEvent.vaultV2(LeadVaultV2.Reply)`,
    under `HostProtocol.Capability.vaultV2` (kind 7), app only, handled by one hook line into
    `Sources/VibeHost/V2/VaultV2Handler.swift` (kind 4), which refuses on the Mac, where the capability isn't listed;
    the vault's saved state gains `v2: LeadVaultV2.Book?` (kind 6); `case .seal` and `case .verify` gain one hook line
    each (kind 4, Linux only): a `.user` seal's id and time are recorded, and a `.user` id that was retired or is older
    than 15 minutes verifies false. The payloads live in `Sources/VibeCore/V2/LeadVaultV2.swift`. No user confirmation
    is needed.
12. **EN-D12: Starting a host is not the engine's.** The server is the host's child, so `HostClient`'s start, replace,
    handover and reap code (`HostClient.swift` 183-221, 293-366, 527-650) is the node's `start`, `stop` and install
    (the bootstrap path's step 8). `HostClientReapTests`' two cases are ported there, against the no-systemd `stop`.
13. **EN-D13: The lead's and the roles' program is the file `claude` resolves to, run by its absolute path, with no
    shell and no setting.** `claude` is never looked up on PATH: the unit's PATH doesn't hold its folder (the bootstrap
    path's step 8), and `~/.local/bin/claude` links into `~/.local/share/claude/versions`, which holds files named by
    version only (2.1.322 here). At each lead's start the server resolves the link it is given with `realpath`, no
    shell, and refuses unless the target is an executable regular file: on the user's node
    `<home>/.local/bin/claude` (the home from `getpwuid`); on a scratch node only `<root>/v2/test/claude`, a link a test
    puts there (to `FakeClaude`'s launcher). Never through `$SHELL -l -i` (`LoginShellCommand.resolve` runs
    `~/.bashrc`, which any worker can edit). `lead`'s confirmation prints the absolute path before the typed code. The
    lead's session gets that path as `VIBESWITCHER_CLAUDE`, and its tool server starts workers and verifiers with it:
    one hook in `vibeswitcher-mcp`'s `command(_:root:)` (`main.swift:240-248`) into
    `Sources/VibeCore/V2/RoleProgram.swift`, which on Linux, with the variable set, answers that path and reads
    neither the settings' `claudeCommand` nor the launch presets (files under `~/.vibeswitcher` any worker can write,
    which today pick the program every worker and verifier runs with its role's grant). The app's `claudeCommand`
    setting is not ported before the bootstrap for the same reason.
14. **EN-D14: The user's messages and the reports go to the lead the vault binds.** The target of a delivery is the
    session the vault binds to the project's lead role (`LeadVault.current(.lead, root:, task: nil)` through
    `HostLink.vault`); the lead the board names is a cross-check. On a mismatch the message is held and `status`
    carries a notice. A worker that names its own session as the lead in `board.json` gets nothing.
15. **EN-D15: The journal is the command line's.** The command line reads `journalctl --user` and `systemctl --user
    show -p Result,ExecMainStatus,ExecMainStartTimestamp` itself (`/usr/bin`, by absolute path), and writes the
    journal entries itself. An entry explains a start, records an acknowledgment or records a request only when
    journald's own fields (`_UID`, `_SYSTEMD_CGROUP`) pass the voice rule's scope list; an identifier the entry carries
    is never enough. The server reports only what it holds (sessions, leads, cards, the requests it accepted, the
    host's notes); what it says about itself is never the record (S2).

## Review Focus

1. No request changes state unless its voice passed on the server, with every unreadable field counted as "not the
   user's voice"; a request whose sender isn't the accepted process closes the connection (E1, E4, E6).
2. Nothing shown to the user as an approval comes from `board.json`; an answer is bound to the card id held in the
   server's memory and recorded in the vault before the lead is told or a merge is approved (E6).
3. Nothing in a file the server keeps is taken as the user's after a restart: not an answer, not a held message, not
   a question (E5, E6, E8).
4. Every host call made in the server goes through the connector; a path connection from the server would be
   `.unknown` and is never made (E1, E2).
5. A wake-up is typed once, into an empty input box, into the lead the vault binds and the board names at the moment
   of typing, never into a shell the agent left (E5).
6. The Mac: the app and its tests untouched; every shared-file edit is one this plan lists, and its Mac form is
   today's behaviour (`NodeQuestionPost` and the vault's two hook lines do nothing where
   `Platform.CodeIdentity.isAvailable`; the Mac's host doesn't list `vaultV2` and refuses it), each with a Mac test.
7. What a worker or a turned lead wrote (question text, commit subjects, file names, task titles, command lines)
   reaches the user's terminal only through `ConfigSeal.inert` (E1, E6, E8).

## The protocol

The seed of stage 3's live protocol: request and reply only, no subscriptions, no events but `bye`.

**Messages.** Each a JSON object on one line.

| Message | Direction | Fields | Notes |
| --- | --- | --- | --- |
| `hello` | server → client, first, unasked | `v` (1), `kind: "hello"`, `node`, `epoch` (a UUID made at each server start), `server` (`commit`, `startedAt`, `pid`), `host` (`startedAt`, and the host's notes when its welcome lists `hostNotes`), `kinds` (the request kinds this server takes), `peer` (the voice this connection has, and why when it isn't the user's), `rule` (`systemd` or `weaker`, EN-D3's voice rule mode) | rule 8's epoch; a client that sees a new epoch knows the server restarted |
| request | client → server | `v`, `id` (the client's, unique on the connection), `kind`, `args` (object), `action` (a UUID, on every state-changing kind), `must` (bool, default false) | |
| reply | server → client | `v`, `re` (the request's id), `ok`, then `result` (object) or `error` (`code`, `message`) | exactly one per request |
| `bye` | server → client, then close | `v`, `kind: "bye"`, `reason` | the last message before the server closes a connection |

**Rules.** Rule 3: a message may gain fields, and readers ignore fields they don't know. A request of a kind the server
doesn't take is answered `unknown-kind` and the connection stays open; with `must: true` the answer is followed by
`bye` and the close. A request with a `v` higher than the server's is answered `version`, then `bye`. A line that
isn't a JSON object, or is over 1 MiB, gets `bye` and the close. A request whose bytes came from a process other than
the one accepted (S5's rule on this socket) gets no reply: `bye`, the close, and a line in the server's log.

**Error codes:** `unknown-kind`, `version`, `bad-args`, `voice` (refused for the voice or a wrong code; the message
says which field failed), `refused` (the engine's reason), `not-yet` (the host link isn't welcomed yet; retry), `gone`
(the card or session is no longer there), `internal`.

**Kinds**, each with the voice it needs (S3: anything not listed is refused). "Code" is EN-D5's typed word: "card" is
checked by the server, "own" by the command line alone.

| Kind | Args | Result | Voice | Code | Task |
| --- | --- | --- | --- | --- | --- |
| `status` | | sessions, leads, cards (counts), the accepted user's-voice requests, notices, the host's notes | anyone of the uid | no | E1; leads E4, cards E6 |
| `questions` | `project`, `all` (bool: closed ones too) | cards: questions, approvals, held config, base moves | anyone of the uid | no | E6 |
| `start` | | the node's start time (it is running) | the user's | no | E1 (starting a stopped node is step 8's, without the server) |
| `stop` | | sessions ended, then the host shuts down | the user's | own | E1 |
| `lead` | `folder`, `goal`, `takeHead`, `replace` | project id, session id, what happened (`started`, `shown`, `waiting`), the program's absolute path | the user's | own | E4 |
| `answer` | `card`, `text`, `code` | the outcome, and what became of an approval | the user's | card | E6 |
| `hold` | `card`, `code` | the held question | the user's | card | E6 |
| `config.held` | `project` | a card bound to the hashes shown, the items (name, change time, size, hash prefix, what changed), the floor `workflow.md` proposes | the user's | no (changes nothing) | E6, E8 |
| `config.accept` | `card`, `code` | sealed, and anything held again | the user's | card | E6, E8 |
| `base.show` | `folder`, `from` (optional commit) | a base-move card: base, from (and whether it is verified), to, the commits (`git log from..to`) | the user's | no | E6, E8 |
| `base.accept` | `card`, `code` | the head now recorded | the user's | card | E6, E8 |
| `base.keep` | `card`, `code` | kept refused, not asked again until it moves | the user's | card | E6 |
| `hooks.install`, `hooks.remove` | `agent` | | the user's | own | the bootstrap path's step 8 |

`status --ack` and `start`'s acknowledgment of the S11 list are not server requests: the command line writes each as
a journal entry (EN-D15), after its own typed code.

**The user's voice** (S3): a peer of the server's uid whose cgroup is outside `user@<uid>.service` and outside the
node's unit, and is one of the scopes E1 measured and lists (`/init.scope` here, `session-*.scope` with ssh); whose
ancestry holds no live session's program, no parser, not the server and not the host; whose controlling terminal is no
session's; whose environment has no `VIBESWITCHER_SESSION`; and that isn't under a `BranchCode` runner. Each field is
read from `/proc` for each request; one that can't be read fails the rule. The rule's mode is fixed once, at the
server's start, from the server's own cgroup: inside `…/user@<uid>.service/…/vibeswitcher-node.service` it is the
systemd rule; a scratch server takes the scopes its test gives through the scratch host's `--server-arg
--test-user-scopes=…` (stage 2's channel, kept across handovers); anything else is the weaker
rule (the other four lines), and `status` says so. No file a worker can remove decides it. The live sessions' programs
and terminals come from `HostLink`'s list.

**Every accepted user's-voice request** is (in this order) recorded in the vault with its action id and digest (E6's
`vaultV2` request; before E6, in the server's memory), acted on, and kept in the server's list of the last 50 that
`status` shows (kind, card or project, when, pid, cgroup, command line). The command line writes it to the journal
(ids and hashes only: no answer text, goal or screen content). `status` marks a request the server accepted that has no
journal entry, and a journal entry whose `_SYSTEMD_CGROUP` isn't a terminal scope.

## Changes to the security document

The plan differed from the security document in these places, each the author's call for the reason given. The
security document took all six in the consolidation of 2026-11-13 (S3's table and Principals, S11 items 7 and 29, T41);
they are kept here as the record of why.

- **The typed word on `lead` and `stop`** (EN-D5): S3's table asks none; its general rule covers them. The code is
  the command line's own for both (no card), a guard rail.
- **No typed word on `config held`** (EN-D5): S3's table groups it with `config accept`; it changes nothing, and the
  card it makes is what `config accept` takes, with the code.
- **`status --ack` and the S11 acknowledgment are journal entries the command line writes**, not server requests (EN-D15,
  as S2 asks for the journal itself); S3's table lists `status --ack` as a request.
- **Sessions post questions** (EN-D10): the Principals table and S3 give sessions `status` and `questions` only; the
  lead's tool server also posts `question.post`, `question.revise` and `question.withdraw`, each sealed by the host as
  the lead's.
- **T41 is narrowed, not closed** (EN-D11): a `.user` seal expires after 15 minutes or once retired; a replay inside
  that window is delivered once. S11 item 29 says so.
- **The delivery target is the vault's lead** (EN-D14), a route S11 item 7 doesn't name: a worker that names its own
  session as the lead in `board.json` would otherwise receive the user's answers.
